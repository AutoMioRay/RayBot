# WebSocket 侧完整安全测试方案
## 一、范围定义
### In Scope（测试对象）
| 模块 | 测试重点 |
|---|---|
| `api/gateway.py` | 连接建立、Identify、心跳、Resume、错误码分支 |
| `api/base.py` | access_token 获取/刷新/存储、单飞、401 重试 |
| 事件模型层 | JSON 反序列化、字段类型、缺失/异常字段处理 |
| 连接管理层 | 断线重连、连接池、并发连接 |
| 日志与异常路径 | 敏感信息泄露、异常栈暴露 |
| 配置加载 | 环境变量、默认值、校验 |
### Out of Scope（另案测试）
- Webhook 侧的 Ed25519 签名验证（独立测试）
- HTTP 主动 API 调用（单独测试 SSRF/证书验证/请求构造）
- 业务中间件层（人设/记忆/工具调用，等中间件上线后再测）
- 依赖供应链 CVE 扫描（放 CI 常规项）
## 二、威胁模型（STRIDE 映射）
| STRIDE 类别 | WebSocket 侧具体威胁 |
|---|---|
| **S - Spoofing** | 伪造 session_id 尝试 Resume；伪造网关服务器（MITM）；token 伪造 |
| **T - Tampering** | 事件 payload 被篡改后注入恶意字段；opcode 混淆 |
| **R - Repudiation** | 关键操作（连接、重连、token 刷新）无审计日志 |
| **I - Info Disclosure** | token/secret 泄露到日志/异常栈；调试模式暴露内部结构 |
| **D - DoS** | 恶意服务器返回超长消息/嵌套 JSON 炸弹；无限重连循环；事件洪峰 |
| **E - Elevation** | 通过恶意事件 payload 触发未预期行为（如注入命令、触发异常 API 调用）|

| ID | 测试项 | 方法 | 预期 | 验收指标 |

| S2-01 | token 仅存于内存 | grep 所有持久化调用 | token 不写文件/不进 Redis | 静态断言 + 集成验证 |
| S2-02 | token 不进日志 | 单测：`caplog` 捕获 | 任何日志级别均不含完整 token | 0 命中 |
| S2-03 | token 不进异常栈 | 单测：抛异常后检查 `traceback.format_exc()` | 栈中不含 token 字符串 | 0 命中 |
| S2-04 | secret 不进入 User-Agent / HTTP header 泄露 | 抓包验证 | 仅出现在请求体指定字段 | 0 命中 |
| S2-05 | 单飞正确性 | 100 并发过期刷新 | 仅发出 1 次刷新请求 | 1 次 |
| S2-06 | 预刷新时机 | 模拟剩余 60s 触发 | 在 < 60s 时后台刷新，业务无感知 | 刷新在业务请求前 |
| S2-07 | 刷新失败降级 | mock 刷新返回 5xx | 不死循环、退避后重试、最终抛出明确异常 | 有退避 + 有上限 |
#### 2.2 JSON / 事件解析器 Fuzz
**工具**：`hypothesis`（策略化 Fuzz）
```python
@given(st.recursive(
    st.none() | st.booleans() | st.integers(-2**63, 2**63) | st.text(),
    lambda children: st.lists(children) | st.dictionaries(st.text(), children),
    max_leaves=200,
))
def test_event_parser_rejects_or_accepts_safely(payload):
    # 所有合法 JSON 输入，解析器要么返回正确模型，要么抛出明确异常，不崩溃
    try:
        parse_event(payload)
    except (ValidationError, ParseError) as e:
        assert isinstance(e, (ValidationError, ParseError))
```
**用例矩阵**：
| ID | 输入类别 | 预期行为 | 验收指标 |
|---|---|---|---|
| S2-08 | 超长字符串（10MB） | 拒绝，有 max_length | 拒绝率 100% |
| S2-09 | 深度嵌套 JSON（10000 层） | 拒绝或递归深度限制 | 拒绝率 100% |
| S2-10 | 缺失必填字段 | 抛 ValidationError | 拒绝率 100% |
| S2-11 | 字段类型混淆（string vs int vs null） | 严格拒绝 | 拒绝率 100% |
| S2-12 | Unicode 边界（零宽字符、组合字符、BOM） | 按 UTF-8 规范处理，不崩溃 | 0 崩溃 |
| S2-13 | 非法 opcode（未知数值） | 抛明确异常，不静默处理 | 拒绝率 100% |
| S2-14 | 超大 payload（HTTP body > 10MB） | 拒绝读取 | 有 max_size 限制 |
| S2-15 | JSON Bomb（`{"a":{"a":{...}}}` 指数展开） | 拒绝（限制 depth/size） | 0 崩溃 |
| S2-16 | 重复键（`{"a":1,"a":2}`） | 明确处理策略（拒绝或取最后） | 有策略，不静默 |
**指标**：Fuzz 输入拒绝率 **100%**；Fuzz 覆盖 10,000 个样本，崩溃数 **0**

## 六、vibe coding 场景的特殊防御
这是方案里最重要的部分——**LLM 生成代码的典型漏洞需要专项测试**：
| 典型 LLM 错误 | 对应测试 |
|---|---|
| `except: pass` 吞掉安全异常 | S1-05 静态规则 |
| 忘记校验 `verify=...`，默认关闭证书 | S3-02/03 MITM 测试 |
| f-string 直接嵌入 token 到日志 | S2-02/03 泄露测试 |
| async 代码中用了阻塞 IO（阻塞事件循环） | S4-09 CPU 尖峰测试 |
| token 刷新无锁，并发时多次刷新 | S4-13 并发单飞 |
| WebSocket 重连无上限 | S4-12 无限重连 |
| JSON 解析用 `json.loads` 无深度限制 | S2-09 嵌套深度 |
| Resume 失败后仍继续 Resume（死循环） | S3-11 |
| 恶意 gateway URL 未校验（SSRF） | S5-05 |
| `ssl=False` 作为默认参数 | S1-01 静态规则 |
**专项建议**：写一个 `tests/llm_specific/` 目录，把以上 10 条做成必测用例，每次重构后跑一遍。

## 八、一句话收敛
**这份方案的核心逻辑：vibe coding 生成的 WebSocket 代码，安全性不在"写对了没有"，而在"边界情况崩了怎么办"**——所以测试重心在 Fuzz（解析边界）、协议分支（错误码完备性）、资源（泄漏与洪峰）、外部模拟（恶意服务器与配置），而**不是**"代码逻辑是否优雅"。LLM 写出的"好看"代码可能隐藏着 S3-11 这种死循环 bug，也可能在 S5-05 上留一个 SSRF 后门——这些只能靠测试抓出来，不能靠 review 抓出来。
把这套方案里的 P0（🔴 L1-L3）先跑通，再逐步把 L4/L5 纳入 CI，就能在保持"天级迭代速度"的同时，把安全兜底做到"周级完善"——这正是 vibe coding 项目能长期存活的关键。
