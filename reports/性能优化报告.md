# 性能瓶颈分析与优化报告 RayBot v0.2.0

- 日期：2026-10-30
- 依据：`提速.md`（底层 SDK 性能优化方向）12 项建议 × 本项目实际结构逐项评估
- 方法：先读代码定位真实瓶颈 → 实测微基准（`tools/bench_json.py`，可复现）→ 只实施"合理项"
- 平台：Windows 10，Python 3.13.12；官方 API 实测连通（appid 1906047398）

## 一、结论速览

原实现的整体架构已经吸收了大部分"提速.md"的最佳实践：**有界队列 + 固定 worker 池、token 单飞 + 后台预刷新（80% TTL + 抖动）、单一共享 httpx 连接池、网关地址整连接复用、Deduplicator/ReplySequencer 均摊 O(1) 逐出**。因此本轮增量集中在三处：

1. **解析层**（orjson 接入，提速.md P0）——实测解码 2.4~2.5x、编码 9.8x；
2. **事件分发热路径**（订阅表缓存化，提速.md 未列但同类）——实测 3.2x；
3. **传输层长尾**（请求体预序列化、debug 计时守卫、`upload_bytes` 哈希出循环）。

未采纳的项目均有实测证据或结构性理由（见第三节），不是跳过而是"评估后否决"。

## 二、已实施项与实测数据

### 2.1 orjson 替代标准库 json（P0）✅

新增 `RayBot/core/_json.py` 统一编解码层：orjson 存在时走 Rust 路径，否则回退 stdlib（调用方零分支）。接入点：

- WS 接收 `_decode`：直接 `loads(bytes/str)`，省去 stdlib 路径的显式 UTF-8 解码；
- WS 发送 `_send`：`dumps()` 返回紧凑 UTF-8 bytes 直接 `ws.send()`；
- HTTP 请求体：`APIClient.request` 预序列化一次（重试路径复用同一 bytes，此前每次重试重复 `json.dumps`），经 `content=` 发送绕过 httpx 内部序列化；
- HTTP/令牌响应体：`loads(response.content)` 直接从 bytes 解析；
- 去重键兜底：`event_dedup_key` 的 sha1 指纹改用 `dumps(event.raw)`。

实测（`tools/bench_json.py`，660B 典型群消息事件载荷，1s×多次取样取中位）：

| 操作 | stdlib json | toolkit 编解码层 | 加速 |
|---|---|---|---|
| loads(str) | 222,997 ops/s | 546,107 ops/s | **2.4x** |
| loads(bytes) | 196,204 ops/s | 493,150 ops/s | **2.5x** |
| dumps | 345,141 ops/s | 3,366,176 ops/s | **9.8x** |

（载荷含大量 CJK 文本；纯 ASCII 小载荷加速比更高。提速.md 预估 5~10x 的上限区间出现在纯序列化场景。）

**安全同向**：orjson 严格 UTF-8 与固定深度上限使 S2-09/S2-15（嵌套炸弹）从"未捕获异常"变为"正常拒绝"，与 V-01 修复协同。

### 2.2 EventBus 订阅解析缓存化（热路径）✅

原实现每条事件分发都执行 `list(per-name) + list(all)` 再 `sort`（订阅时已排序）。改为按事件名缓存合并后的不可变 tuple，任何订阅变更（注册/注销/once 触发/错误订阅移除）定向失效缓存。

实测：**175 万 → 565 万 ops/s（3.2x）**，且高频事件路径从"每事件两次堆分配 + O(n log n) 排序"降为零分配。正确性由与参考实现逐步对比的断言 + 既有订阅/注销测试保证。

### 2.3 请求体预序列化 + debug 计时守卫 ✅

- `APIClient.request` 中 JSON body 只序列化一次（bytes），重试路径直接复用；原来每次尝试都重新 `json.dumps`。
- `logger.debug` 的 `perf_counter` 差值计算被 `isEnabledFor(DEBUG)` 守卫——生产路径每请求省两次系统调用与字符串格式化。

### 2.4 `upload_bytes` 哈希移出事件循环 ✅

三重哈希（md5 + sha1 + 10MB 窗口 md5）改为 `asyncio.to_thread`，与 `upload_file` 路径对齐。消除 5MB 上传时的事件循环停顿（实测该量级哈希 ~10-30ms，事件洪峰下即 P99 尖刺来源）。

### 2.5 背压策略补全（drop 模式）✅

EventBus 新增 `overflow` 参数：

- `"block"`（默认，行为不变）：队列满时 `await put`，背压传导至 WS 接收循环——**不会**阻塞心跳任务（心跳是独立 task），但长时间停住接收循环会被服务器断开；
- `"drop"`：队列满即丢弃 + 计数（`stats["dropped"]`）+ 分级告警（首滴即警，此后每 100 次一条），接收循环永不停。

按提速.md 的建议提供 drop 语义；默认保持 block 以免静默丢事件，高频机器人可显式切换（`GatewayConfig.dispatch_overflow="drop"`，Bot 已接线）。

### 2.6 轻量观测（替代 OpenTelemetry）✅

- `GatewayClient.stats`：events_received / events_dispatched / duplicates_ignored / invalid_payloads；
- `EventBus.stats`：published / processed / dropped / queued / workers。

选择不引入 OpenTelemetry 依赖：本项目单进程、无分布式拓扑，四个计数器即可回答"积压在哪一环"；正式 trace 属于运维平台建设，由业务侧按需接入。

### 2.7 uvloop（P1，条件采纳）✅ 部分

`pyproject.toml` 新增可选依赖组 `RayBot[uvloop]`（`sys_platform != 'win32'` 标记）。本测试主机为 Windows，uvloop 不可安装——标准循环保持默认，Linux/macOS 部署可在入口 `uvloop.install()` 获得提速.md 预估的 2~4x 调度加速。未在库内强装：事件循环策略属于应用层选择。

### 2.8 Token 预刷新 + 单飞（P0）✅ 已在位 + 增强

原实现即满足提速.md 要求：单飞锁 + 后台在 80% 剩余 TTL 时刷新（含 0~10% 抖动防抖群）+ 失败 30s 退避重试。本轮**增强**：force_refresh 并发单飞（见《漏洞修复报告》V-05），消除强制刷新路径的请求风暴长尾。

## 三、评估后不采纳项（含理由）

| 提速.md 条目 | 结论 | 理由 |
|---|---|---|
| 2. Pydantic v2 `model_validate_json` | **不采纳** | 本项目不使用 Pydantic；事件模型为手写 slots dataclass + 定向字段提取，本来就是"单步解析"，无"dict 构造→再验证"三步可合并。引入 pydantic-core 反而增加每事件构造开销与依赖面 |
| 6. `msgspec.Struct` 替换事件模型 | **不采纳** | 平台字段类型不稳定（数值/字符串混发），现有 `as_str/as_int` 宽容转换是刻意的健壮性设计；msgspec 默认严格匹配会在真实事件流上炸。且 17 个事件类的整体替换是 API 破坏性变更，风险收益不成比例（提速.md 预期收益 10~20%，而解析层 orjson 已拿下大头） |
| 5. HTTP/2 多路复用 | **不采纳（实测否决）** | 实测官方 API：`curl` ALPN 仅提供 http/1.1、服务器接受 http/1.1；`httpx(http2=True)` 协商结果 **HTTP/1.1**。`api.bot.qq.com` 不支持 h2，启用无任何收益。保留 `HTTPConfig.http2` 开关供自建网关/代理场景使用 |
| 7. 惰性字段解析 | **不采纳** | 当前模型只提取声明字段，大字段（attachments/msg_elements）本就按需构造，`raw` 浅持有不深拷贝；无"必须惰性才免于解析"的大字段 |
| 10. 响应体流式解析 | **不采纳** | 机器人场景 JSON 响应为 KB 级；httpx 已缓冲，流式仅对批量富媒体下载有价值——当前无此接口，留待引入时一并实施 |
| 12. Ed25519 验签并发 | **不适用** | Webhook 已封藏，验签路径不复存在 |
| 9. 中间件短路/并行 | **不适用** | 无中间件链；订阅优先级缓存（2.2）消解了同类的每事件重复计算 |

## 四、延迟预算验证（对照提速.md 经验分布）

实测结构（事件到达 → 回复发出）：

| 环节 | 提速.md 经验占比 | 本项目实测/推断 | 本轮动作 |
|---|---|---|---|
| JSON 解析 + 模型构造 | 15~30% | 解析层 orjson 化后大幅下降；模型构造为定向字段提取，本就轻 | ✅ 2.4~2.5x |
| API 调用网络 + token | 40~60% | 连接池/单飞/预刷新已在位；h2 被实测否决；预序列化小幅增益 | ✅（既有 + 增强） |
| 事件循环调度 | 5~15% | Windows 无法用 uvloop；热路径去分配（缓存化）部分对冲 | ✅ 3.2x（分发解析） |
| 队列/去重/序号 | — | 均摊 O(1)，无热点 | — |

综合估算：事件侧固定成本（解析+分发解析）合计约降至原来的 **50~60%**，与提速.md 的收敛预期一致；API 调用侧长尾（token 刷新尖刺）原实现即已消除，本轮补齐强制刷新单飞。
